# 외부 구조 보고서 작성 가이드

> 최종 갱신일: 2026-07-08  
> 대상 문서: `mission_control/EXTERNAL_STRUCTURE_REPORT.md`  
> 목적: 구조 보고서를 장기 아키텍처 문서로 유지하기 위한 작성·갱신 기준

## 문서의 정체

`EXTERNAL_STRUCTURE_REPORT.md`는 다음을 위한 문서다.

- **장기 아키텍처 문서**: Phase 10, Phase 11 이후에도 대부분 안정적으로 남는 구조 설명
- **신규 AI 작업자 온보딩 문서**: 코드베이스 전체를 읽지 않아도 책임과 경계를 이해하도록 돕는 진입점
- **책임과 경계 설명서**: 모듈이 무엇을 하고, 무엇을 하지 않는지 정의

이 문서는 다음이 **아니다**.

- 진행률 보고서
- 작업 로그
- 마이그레이션 일지
- 검증 보고서
- 태스크 보드

## 정보 소유권 비교

| 문서 | 소유하는 정보 |
|---|---|
| `EXTERNAL_STRUCTURE_REPORT` | 아키텍처, 모듈 책임, 런타임 흐름, 데이터 경계, 확장 지점, 외부 협업 기준 |
| `CURRENT_STATE` | 현재 구현 상태, 검증 결과, 테스트 수, 번들 크기, 다음 우선순위 |
| `TASK_BOARD` | 작업 ID, 상태, 완료 조건, 작업 범위 |
| `WORK_LOG` | 작업별 세부 이력, 수정 파일, 검증 결과 |
| `HANDOVER` | 작업 인수인계, 주의사항, 최신 흐름, 검증 기준 |

`EXTERNAL_STRUCTURE_REPORT`는 위 문서들의 정보를 **요약하거나 참조**할 수 있지만, **대체하거나 중복 저장하지 않는다**.

## 작성 원칙

1. 현재 구현된 사실과 앞으로의 희망 사항을 분리한다.
2. 추천 엔진, 대사 계층, UI 연출, 캐릭터 설정을 섞어 쓰지 않는다.
3. 외부 AI가 오해하기 쉬운 금지선을 먼저 적는다.
4. 파일 경로는 실제 경로를 쓴다.
5. 검증 상태는 외부 보고서가 아니라 `CURRENT_STATE.md`가 소유한다. 필요하다면 "검증 상태는 CURRENT_STATE.md 참조" 한 줄로 충분하다.
6. 카루아 말투나 시에스타 역할은 요약하되, 최종 원문 기준은 내부 문서로 연결한다.
7. 외부 AI에게 코드 구현을 요청하지 말고 기획·샘플·검수 기준을 요청한다.

## 항상 우선할 내용

아래 주제는 문서의 핵심이며, 갱신 시 항상 우선한다.

- 아키텍처와 모듈 간 책임 경계
- 런타임 데이터 흐름
- 확장 지점과 제약 조건
- 변경하면 안 되는 핵심 결정
- 외부 협업자가 알아야 할 구조적 맥락

## 축적을 피해야 할 내용

아래 정보는 문서를 불필요하게 길게 만들고, 자주 구식이 되어 유지보수 부담을 증가시킨다. `CURRENT_STATE.md`, `TASK_BOARD.md`, `WORK_LOG.md`, `HANDOVER.md`가 소유하며, 외부 보고서는 필요할 때만 링크로 참조한다.

- 현재 Phase 진행률(%)
- 마이그레이션 완료 slice 수
- 테스트 통과 개수
- 번들 크기
- 임시 로드맵
- 다음 작업 목록
- 검증 이력
- 작업별 완료 일지

## 갱신해야 하는 경우

아래 중 하나라도 바뀌면 `EXTERNAL_STRUCTURE_REPORT.md`를 갱신한다.

- 모듈의 책임 경계가 바뀐 경우
- 런타임 데이터 흐름이 바뀐 경우
- 핵심 아키텍처 결정이 변경된 경우
- 외부 AI에게 넘길 과제 범위가 바뀐 경우
- 새로운 확장 지점이 추가된 경우

## 갱신하지 않아도 되는 경우

아래 변경은 `WORK_LOG.md`, `CURRENT_STATE.md`, `TASK_BOARD.md`에만 기록한다.

- 구현 진행률 변동 (Phase % 증가, slice 완료)
- 테스트 수나 번들 크기 변동
- 내부 함수명만 바뀐 리팩토링
- 외부 기획자가 알 필요 없는 구현 세부 버그 수정
- 아직 승인되지 않은 아이디어 메모
- 작업 우선순위 조정

## 단순화 규칙

`EXTERNAL_STRUCTURE_REPORT.md`를 갱신할 때는 다음 순서를 고려한다.

1. **오래된 정보를 교체한다.** 새로운 설명이 더 낫다면 기존 문단을 지우고 다시 쓴다.
2. **중복된 섹션을 병합한다.** 같은 주제가 여러 곳에 나뉘어 있다면 하나로 합친다.
3. **더 이상 필요 없는 설명을 제거한다.** 완료된 작업의 상세 진행 과정은 유지할 가치가 없다.
4. **항상 추가보다 대체를 우선한다.** 문서가 더 길어지는 것이 아니라 더 명확해져야 한다.

## 권장 구조

외부 구조 보고서는 다음 순서를 유지한다.

1. Project Overview (프로젝트 한 줄 요약)
2. Core Design Principles (반드시 지켜야 하는 핵심 경계)
3. Runtime Architecture (전체 데이터 흐름)
4. Major Modules (주요 파일 지도와 모듈 책임)
5. Responsibility Boundaries (모듈 간 책임 경계)
6. Dialogue Architecture (대사 구조와 계층)
7. Recommendation Architecture (추천 시스템 구조)
8. Session & Context (세션 흐름과 컨텍스트)
9. ResponsePlan (대사 DB 계약과 이관 방향)
10. Data Ownership (데이터 출처와 소유권)
11. Extension Points (향후 확장 지점)
12. External Collaboration Guidelines (외부 기획자 협업 기준)

섹션을 추가할 수는 있지만, 외부 AI가 빠르게 읽어야 하므로 중복 설명보다 기존 섹션의 갱신을 우선한다.

섹션 9~12는 필요하면 더 짧은 참조 링크로 대체할 수 있다. 예: "ResponsePlan 상세는 CURENT_STATE.md 참조"

## 외부 AI에게 전달할 때

외부 AI에게는 보통 아래 3개를 함께 전달한다.

1. `mission_control/EXTERNAL_STRUCTURE_REPORT.md`
2. `mission_control/CONVERGENCE_PRINCIPLES.md`
3. 현재 받고 싶은 기획 질문 또는 과제 문장

말투 검수가 핵심이면 `mission_control/CHARACTER_DESIGN.md` 또는 `bar_tend/src/lib/bartender/persona.ts`의 관련 부분을 추가로 전달한다.

구현 구조 검토가 핵심이면 `mission_control/ARCHITECTURE.md`를 추가로 전달한다.

## 외부 AI에게 요청하기 좋은 것

- 카루아 말투 금지 규칙 정리
- 대표 사용자 입력과 반응 방향
- `reaction / lead / recommend / explanation` 블록 샘플
- intent별 문단 구조
- 상태·요청별 대사 풀 설계
- 시에스타와 카루아의 말투 차이
- 대사 품질 검수 체크리스트

## 외부 AI에게 요청하지 않는 것

- 바로 코드 구현
- 추천 알고리즘 교체
- DB에 없는 칵테일 사실 생성
- 출처 없는 역사·유래·창작자 생성
- WebLLM이 추천 결과를 정하는 구조
- 카루아를 상담가처럼 만드는 위로 대사
- 시에스타를 상시 대화 캐릭터로 확장하는 설계

## 결과물을 가져온 뒤 처리

외부 AI가 만든 기획안은 바로 코드에 넣지 않는다. 먼저 아래 순서로 검수한다.

1. 추천 프로세스를 앞으로 미는가
2. 상담원식 대사가 아닌가
3. 술이 감정 문제의 해결책처럼 보이지 않는가
4. 현재 JSON/프리셋 구조에 옮길 수 있는가
5. 카루아와 시에스타의 역할을 섞지 않는가
6. 추천 엔진과 대사 표현 계층을 섞지 않는가

검수 후 반영할 내용은 `TASK_BOARD.md`의 해당 작업에 연결하고, 실제 반영 이력은 `WORK_LOG.md`에 남긴다.
