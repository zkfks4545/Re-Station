## DEC-021: 입력 경로 기반 대사 트리거

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-06-16 |
| 상태 | 승인 |
| 결정 내용 | 대화 소재와 대사 풀은 추천된 칵테일 자체가 아니라 사용자가 그 결과에 도달한 입력 경로가 결정한다. 칵테일은 제조·서빙·정보 카드의 소재로 사용하고, "왜 이 칵테일인가"를 말하는 대화는 주문 방식, 감정·무드, 취향 신호, 재료·베이스 언급, 직접 이름 주문, 추론 종료 같은 경로 맥락을 따른다. |
| 이유 | 같은 네그로니라도 쓴맛 선호 끝에 도달한 경우와 캄파리 언급으로 도달한 경우, 이름을 직접 주문한 경우는 사용자가 기대하는 대화 소재가 다르다. 칵테일 ID만으로 대사를 고르면 반복감이 커지고 입력 맥락이 사라진다. |
| 기존 구조와의 관계 | DEC-003, DEC-015, DEC-019는 유지한다. 추천 결과와 근거는 DB·규칙 엔진이 확정하고, 새 대사 트리거 계층은 확정된 결과에 `route`, `routeTags`, `dialogueState`, `affectState`, `facts`, `forbidden`을 붙여 적절한 대사 풀, 말투, 표정 스프라이트, 애니메이션을 고른다. WebLLM은 재개하더라도 이 선택을 바꾸지 않고 확정된 문장의 말투만 포장한다. |
| 입력 경로 예시 | `directCocktailOrder`, `anecdoteOrPersonOrder`, `moodOrder`, `tastePreferenceOrder`, `ingredientOrBaseOrder`, `recommendationInference`, `randomPick` |
| 3축 분리 | `route`는 무엇을 이야기할지, `dialogueState`는 어떤 장면의 말투·발화 리듬·애니메이션 클립을 쓸지, `affectState`는 어떤 감정 표정 스프라이트와 세부 어조를 쓸지 결정한다. 칵테일 ID는 제조·서빙 대사의 변수로만 결합한다. |
| FSM 상태 예시 | `idle`, `listening`, `thinking`, `asking`, `recommending`, `serving`, `bantering`, `safety`, `error`, `exiting` |
| 감정 상태 예시 | `neutral`, `warm`, `curious`, `confident`, `playful`, `concerned`, `awkward`, `tired` |
| 대사 풀 원칙 | 주문 방식이 대사 풀을 결정하고 칵테일은 제조·서빙 대사를 결정한다. 직접 이름 주문은 해당 칵테일 일화, 일화·인물 주문은 입력된 일화 관련 대사, 감정·무드 주문은 감정 태그 대사, 추론 끝에 도달한 결과는 중립적인 "이게 맞을 것 같네요" 계열 대사를 사용한다. |
| 반복 방지 | 최근 N개 사용 대사를 제외하고, FSM 상태별 대사 풀을 분리하며, 입력 경로 태그와 감정 상태로 후보를 필터링한다. 같은 상태·같은 경로에서는 `shuffle` 또는 `cycle` 방식으로 순환하고 템플릿 변수 치환으로 칵테일명, 재료, 맛 태그를 주입한다. |
| 구현 방향 | Ink 스크립트의 `shuffle`/`cycle`과 템플릿 변수 치환을 우선 후보로 삼되, MVP에서는 동일 계약을 TypeScript 규칙 엔진으로 먼저 구현할 수 있다. 핵심은 대사 전문을 추천 JSON이나 칵테일 DB에 누적하지 않고, 입력 경로 태그와 작은 대사 풀을 분리해 관리하는 것이다. |
| 금지 | 칵테일 ID만으로 모든 추천 대사·표정·애니메이션을 결정하는 것, FSM 상태가 대화 소재를 덮어쓰는 것, 추천 결과를 바꾸기 위해 대사 트리거 계층에서 후보를 재계산하는 것, 최근 사용 대사를 고려하지 않아 같은 맥락에서 같은 대사가 반복되는 것 |
| 되돌릴 조건 | 입력 경로 기반 대사 선택이 추천 설명을 불명확하게 만들거나, 대사 풀 관리 비용이 MVP 범위를 반복적으로 초과할 때 |

## DEC-020: 칵테일 데이터 확장과 관리자 검증 큐

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-06-16 |
| 상태 | 승인 |
| 결정 내용 | 최종 제품의 칵테일 데이터 확장은 IBA 공식 레시피를 최우선 출처로 사용한다. IBA에 없는 변형 칵테일이나 시그니처 칵테일은 확인된 레시피를 기준으로 후보를 만들고, 프로그램은 레시피에서 벗어나지 않는 맛·향·질감 설명만 보강한다. 정보가 부족하거나 자동 검색으로 확정하지 못한 항목은 정식 칵테일 DB가 아니라 관리자 검증 큐로 보낸다. |
| 이유 | 추천 결과의 사실성은 레시피와 출처 검증에 의존하므로, AI가 이름·레시피·유래를 추정해 정식 데이터처럼 저장하면 오정보가 누적될 위험이 크다. 반면 맛 설명은 입력된 재료와 조주법 안에서 생성하면 제품 경험을 보강할 수 있다. |
| 처리 순서 | 1) IBA 공식 레시피 검색, 2) IBA에 있으면 공식 출처로 추가 또는 갱신, 3) IBA에 없지만 레시피가 명확한 변형·시그니처는 후보 생성 및 맛 설명 보강, 4) 정보 부족·검색 실패·출처 충돌 항목은 관리자 검증 큐로 이관, 5) 관리자 승인 전에는 추천 후보로 사용하지 않음 |
| AI 사용 경계 | AI 또는 프로그램 생성은 재료, 용량, 기법, 베이스, 탄산 여부, 도수 추정, 맛 태그를 근거로 한 설명문과 태그 후보에만 사용한다. 역사, 유래, 창작자, 공식성, 유명세, "클래식", "정통" 같은 권위 표현은 출처 없이 생성하지 않는다. |
| 관리자 검증 큐 | 관리자 검증 큐는 자동 처리로 해결되지 않은 정보 부족 칵테일, 검색 실패 항목, 출처가 충돌하는 항목, IBA에 없는 시그니처·변형 후보를 사람이 판단하는 곳이다. 승인되면 `official` 또는 추천 가능한 상태로 승격하고, 반려되면 `rejected` 또는 보류 처리한다. |
| DB 운영 방향 | 서비스에는 유저 간 상호작용이 없으므로 복잡한 소셜 백엔드는 만들지 않는다. 다만 모든 사용자가 같은 검증된 칵테일 데이터를 보아야 하므로, 최종형에서는 공통 `official` 칵테일 DB와 관리자 검증 큐를 분리해 운영한다. 일반 사용자는 공식 데이터 읽기와 미확정 항목 요청만 가능하고, 쓰기·승격·반려는 관리자 권한으로 제한한다. |
| 백엔드 선택 | MVP와 개인 운영 단계에서는 JSON을 유지한다. 공통 DB가 필요해지는 시점에는 직접 백엔드보다 Supabase 같은 BaaS 또는 얇은 백엔드를 우선 검토한다. 필요한 기능은 칵테일 목록 조회, 미확정 요청 제출, 관리자 로그인, 검증 큐, 승인·반려·승격 정도로 제한한다. |
| 앱 포팅 | 모바일 앱 포팅은 후순위다. 현재 웹 구조를 유지하되, 데이터 접근 계층을 분리해 두면 향후 PWA 또는 Capacitor 앱에서도 같은 공통 DB/API를 재사용할 수 있다. |
| 사용자 응대 | 정보가 부족한 이름은 정식 DB에 바로 추가하지 않는다. 런타임에서는 "그런 이름도 있나요? 흥미롭네요. 아직 확인된 메뉴에는 없어서 추천 후보로 쓰진 않을게요."처럼 흥미를 보이되, 레시피가 확인될 때까지 추천에 사용하지 않는다. |
| 되돌릴 조건 | 신뢰 가능한 공식·관리자 출처 없이도 충분히 검증 가능한 자동 데이터 파이프라인이 마련되고, 오정보 방지 테스트와 수동 검수 대체 기준이 통과될 때 |

## DISC-001: JSON 중심 대화 계약과 미등록 칵테일 발견

| 항목 | 내용 |
|---|---|
| 상태 | DLG-801, DATA-801, DATA-802 구현 완료. 외부 검색·저장 정책은 MVP 이후 검토 |
| 문제 | DB에 없는 칵테일 이름을 주문하면 일반 대화로 빠지거나 대화가 단절될 수 있다. 향후 LLM을 연결하더라도 전체 대화 판단을 모델에 맡기면 비용, 지연, 재현성 부담이 커진다. |
| 제안 | 사용자 입력의 의미와 다음 행동을 `DialogueTurn` JSON으로 구조화한다. 규칙 엔진 또는 LLM은 동일한 JSON 후보를 만들고, 애플리케이션이 스키마 검증 후 상태 변경과 행동을 확정한다. |
| JSON 규모 통제 | 대사 전문과 상황별 문장을 JSON에 누적하지 않는다. 공통 스키마에 `intent`, `entities`, `statePatch`, `action`, `responseGoal`, `facts`, `forbidden`, `confidence`만 담고, 기본 복구 대사만 소수 템플릿으로 유지한다. |
| 실행 역할 | 외부 API는 검색과 출처 수집, 애플리케이션 코드는 스키마 검증·상태 전이·행동 확정, WebLLM은 검증된 `responseGoal + facts + forbidden`을 카루아 말투로 표현하는 역할만 맡는다. |
| 컨텍스트 원칙 | WebLLM에는 전체 대화 전문 대신 최근 대화 요약, 현재 상태, 이번 응답 목표와 검증된 사실만 전달한다. 실패하거나 시간 예산을 넘으면 기본 템플릿을 즉시 사용한다. |
| 미등록 칵테일 흐름 | DEC-020에 따라 IBA 공식 레시피를 먼저 찾는다. IBA에 없고 레시피가 명확한 변형·시그니처는 후보로 만들 수 있으나, 정보 부족·검색 실패·출처 충돌 항목은 정식 DB가 아니라 관리자 검증 큐로 보낸다. |
| 저장 경계 | 정식 칵테일 DB에는 IBA 공식 또는 관리자 승인으로 품질 기준을 통과한 항목만 저장한다. 관리자 검증 큐는 정보 부족 이름, 검색 실패, 출처 충돌, 시그니처 후보를 별도로 보관하며 추천 결정에는 사용하지 않는다. |
| LLM 경계 | WebLLM은 오프라인 임시 설명이나 카루아 말투 포장에 사용할 수 있다. 외부 API 기반 AI는 검색 결과 정규화와 요약 후보 생성에 사용할 수 있으나, 출처 사실과 정식 DB 승격은 애플리케이션 검증 계약을 통과해야 한다. |
| 미결정 사항 | 외부 검색 API, 서버 유무, 사용자별 발견 기록 저장소, 자동 승격 허용 여부, 출처별 신뢰도 정책 |
| 승인 조건 | JSON 스키마, 저장 경계, 실패 복구, 개인정보·비용 정책, 출처 검증 절차를 별도 설계하고 테스트 가능한 완료 조건을 확정할 것 |
